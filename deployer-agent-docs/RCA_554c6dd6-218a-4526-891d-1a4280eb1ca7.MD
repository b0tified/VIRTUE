# RCA — blast-arena-servers: leader pod has higher in-game WS ping than the relayed follower path

## Problem statement
On the live app, in-game WebSocket ping is **higher for clients that land on the leader pod** (the match host) than for clients that land on the follower and are then relayed to the leader — even though the follower path takes an extra network hop (client→ingress→follower→leader). Reported CPU ~4%. Asked to investigate node/AZ placement, ingress/kube-proxy/externalTrafficPolicy routing, direct RTT to pod IPs, node saturation/CPU steal, and per-pod CFS throttling, and explain why the leader path is slower.

## TL;DR
The slowdown is **not** a network / AZ / ingress / kube-proxy issue. It is an **application + capacity** issue: the leader pod runs the entire authoritative game on **one Python asyncio event loop** (GIL = one core), and that loop is the shared bottleneck. Clients connected **directly** to the leader have their ping/pong serviced by that busy loop and queue head-of-line behind the 20 Hz simulation tick + the per-tick fan-out to every socket. Clients routed **via the follower** get their client-facing socket I/O handled by the follower's otherwise-idle loop; the extra in-cluster hop is sub-millisecond (persistent, `TCP_NODELAY`, compression disabled) and is far cheaper than the event-loop queueing time it removes from the leader. tier_0's **250m CPU limit** (≈¼ core) leaves that loop with no burst headroom, so "CPU ~4% average" is misleading — what hurts is per-100ms CFS throttling + event-loop scheduling latency, not mean CPU.

### Tier / capacity (get_tier)
- tier_0 "Starter": **cpu request 50m, cpu_limit 250m**, mem 200Mi/512Mi, fixed 2 replicas, no HPA/VPA. 250m = a quarter of one vCPU is the hard ceiling for the leader's single-threaded event loop.

### Architecture (source: backend/server.py, backend/_lib/cluster.py)
- One pod is elected leader via a Mongo lease (`_lib/cluster.py leader_loop`); every follower runs `ClusterProxyMiddleware` that transparently proxies `/api` HTTP + the `/api/ws/game` WebSocket to the leader. So **all matches, queues, parties live only in the leader's memory**.
- The leader runs the authoritative sim: `Room.run()` (L7644) loops at `TICK_RATE` (20 Hz), calling `await self.tick()` (physics, L6805) then `broadcast()` (L5304) which `asyncio.gather()`s a `send_text` to **every human socket** every 50 ms — all on the single event loop. Comments in-code confirm "the entire 20Hz tick (gather() in broadcast() awaits all sends)" (L5291, L5308).
- In-game ping is an **application-level** message, not a WS control frame: client sends `{type:"ping", ts}`, handler replies `{type:"pong", ts}` at **L6001-6002**, executed on the server event loop. For both direct and relayed clients the pong is produced by the **leader's** loop (the follower only shuttles bytes).
- The follower→leader relay (`_ws`, cluster.py) is deliberately cheap: persistent `websockets.connect`, `open_timeout=3`, `compression=None`, and `TCP_NODELAY` set on the socket. It runs as two byte-pump tasks on the follower's loop, which does **no** simulation.

### Live symptom corroboration (fetch_app_logs)
- Repeated `WARNING - leader 10.75.183.197:8001 unreachable, serving locally for 60.0s` emitted by the follower. This is the follower's relay `connect()` to the leader's `:8001` timing out (2–3 s budget) → `_mark_bad()` → the follower serves matches **locally for 60 s**. A saturated event loop on the leader is slow to `accept()` new TCP connections, which is exactly how a CPU-bound leader produces these timeouts — the same root saturation that inflates ping. (Side effect: during those 60 s windows the follower runs a *separate* in-memory match = split-brain.)

## Why the leader path is slower than the extra-hop follower path
Decompose the ping/pong RTT:
- **Direct (leader) client:** `net(client↔leader)` + `leader loop: time to read the ping` + `emit pong` + `leader loop: time to flush the pong` + `net(leader↔client)`. The two "leader loop" terms are inflated because the loop is mid-`tick()`/`broadcast()` — the ping waits behind simulation + fan-out (on 250m CPU, a tick plus a gather() over N sockets is not free).
- **Relayed (follower) client:** same leader-side processing, **plus** two sub-ms in-cluster hops — but the **client-facing** read of the ping and flush of the pong (and all per-frame WS framing for the 20 Hz state stream the client receives) are done by the **follower's idle loop**, with no head-of-line contention. The in-cluster hop (NODELAY, no compression, persistent) costs far less than the event-loop queue time it removes.

Net: offloading the client-facing socket work to an idle loop more than pays for the extra hop. The leader is slow because its one event loop is the contended resource, not because of the network between ingress and the pod.

Why "CPU ~4%" is a red herring: at a 250m limit the container gets ~25 ms of CPU per 100 ms CFS period. A burst of simulation+fan-out can exhaust that quota within a period; the kernel then throttles (freezes) the whole container until the next period, and a blocked asyncio loop shows up as **latency**, not as sustained CPU%. Mean CPU over a minute stays low while sub-100ms stalls pile onto ping.

## Recommended fixes
### 1. Code (E1) — remove the single-loop / leader-takes-all bottleneck
The follower is pure overhead today (a relay + an extra hop) and the leader's one loop carries every match plus every socket. Options, best first:
- **Shard rooms across pods** — make each pod authoritative for its own matches instead of relaying everything to one leader. This deletes the relay hop entirely and spreads simulation CPU across both replicas.
- If leader-takes-all must stay: **run the 20 Hz simulation off the WS-serving path** (dedicated worker process/thread on its own core) so ping/pong and socket reads aren't starved by `tick()`/`broadcast()`.
- **Prioritize control traffic:** service the `{type:"ping"}` message without waiting behind the per-tick `broadcast()` gather().
- **Soften the relay failure mode:** the aggressive `BAD_LEADER_COOLDOWN_S=60` + 2–3 s connect timeout causes 60 s local-serve split-brain whenever the leader loop is briefly busy; raise/retry the connect and shorten the local-serve fallback.
(Architecture reproduced by reading source in the sandbox; live load/latency could not be reproduced there — no secrets, isolated network.)

### 2. User — raise the tier (Resources)
tier_0's **250m CPU** (≈¼ core) is far too small for an authoritative real-time (20 Hz) game server that also fans out state to every socket on one thread. Move to a tier that grants at least a full dedicated vCPU (more if player counts grow) so the leader loop has burst headroom and stops being CFS-throttled. The 250m ceiling is confirmed via get_tier; the throttling itself is inferred (no counter access), but the loop is unambiguously CPU-bound by design.
