# RCA — "CPU only 4% but every player >100ms ping" (blast-arena-servers / VIRTUE FPS)

## Problem statement
Live prod FastAPI + 20Hz WebSocket FPS. User reports server CPU ~4% yet all players see in-game ping >100ms. Asked to check: pod CPU vs limit + CFS throttling, replica count, whether WS goes through Cloudflare (edge→origin hops), origin region vs player location, nginx WS buffering, raw RTT origin vs CDN, and compare the admin "Server Health" event-loop lag.

## Verdict
**This is a network/geography latency floor, not a server-side problem.** The server adds essentially nothing to the measured ping. The earlier RCA's "event-loop saturation + tier_0 CPU limit" theory is **disproven** by current evidence — CPU is idle and the pong path is synchronous and off the game-tick path.

## What the in-game ping actually measures
- Client sends `{"type":"ping","ts":Date.now()}` — `frontend/src/pages/Game.jsx:641`.
- Server replies **immediately** on receive: `frontend`→ `backend/server.py:5979-5984` → `await self._send(player, {"type":"pong","ts": msg.ts})`. No queueing behind the 20Hz broadcast loop.
- Client computes RTT on pong — `Game.jsx:415`.
- WS endpoint: `wss://{REACT_APP_BACKEND_URL host}/api/ws/game` — `frontend/src/game/network.js:22`. The host is the public `blast-arena-servers.emergent.host`.

So the number is a **pure client→server→client network round trip**. Server contribution is bounded by event-loop lag only (sampled in `_server_health_monitor`, server.py:7721). The 20Hz tick does NOT add to the ping measurement (ping/pong is handled synchronously, not on the tick).

## Evidence
1. **Origin region = AWS us-west-2 (Oregon).** `SERVER_REGION_LABEL="US West (Oregon)"` (server.py:7703); run image is in ECR `...us-west-2...`; cluster `deployment-cluster-03` (us-west-2). Players reported central/east US.
2. **Traffic is proxied through Cloudflare.** `frontend_type=cloudflare`; `blast-arena-servers.emergent.host` resolves to Cloudflare anycast IPs `104.18.14.241 / 104.18.15.241` (measured from eph pod). So the WS path is: client → nearest CF edge (TLS terminate) → CF backbone → origin nginx:8080 → uvicorn:8001. Extra edge hop + backhaul to Oregon; Cloudflare gives no long-haul acceleration for WS (no Argo).
3. **CPU is idle — not throttled.** Tier_0: request 50m, **limit 250m**, 2 replicas, HPA disabled (get_tier). User-observed ~4% CPU ⇒ well under the 250m ceiling, so no CFS throttling. No `OOMKilled`/throttle/evict events in `get_pod_events` (only transient startup-probe 503s during a scale event hours earlier; both pods currently Ready, restart_count 0).
4. **nginx is not buffering the WS.** `nginx.conf` `/api` location sets `proxy_http_version 1.1`, `Upgrade`/`Connection` headers, `proxy_read_timeout 86400`. Once a connection is upgraded, nginx tunnels frames bidirectionally (proxy_buffering does not buffer WS frames). Not a latency source.
5. **Baseline RTT floor to the edge, from a near-origin vantage:** TCP-connect RTT from the eph pod (us-west-2) to the CF edge = **16.1 ms min / 16.9 ms avg** over 6 samples. This is the near-Oregon PoP leg; the player-side long-haul is additive on top of this.

## Baseline network RTT floor (the irreducible part)
Fiber round-trip ≈ real-world ~1ms per ~60–75km round trip after routing overhead:
- West-coast player → Oregon origin: ~**20–40 ms** (should be fine).
- Chicago/central → Oregon: ~**45–60 ms**.
- NYC/east → Oregon: ~**70–90 ms**, and with the client→local-CF-edge leg + CF→Oregon backhaul + TLS, **100 ms+ is the expected floor.**

That matches the report exactly: central/east players sit at/above 100ms because the origin is single-region in Oregon and they are ~3,000–3,900 km away. **No server tuning can beat the speed of light to Oregon.**

## Server-side latency added: ~0 (inferred, not live-measured)
- Pong is sent synchronously on receive (server.py:5979-5984) — no tick coupling.
- Event-loop lag is near-zero at 4% CPU.
- The admin panel route is `GET /api/admin/server_health` (admin-gated, returns `loop_lag_ms`, `loop_lag_max_ms`, per-room `tick_ms`, `db_ping_ms`, `ping_avg_ms/ping_max_ms`). NOTE: the user said `/api/admin/health` — that path 404s; the real path is `/api/admin/server_health`. I could not read live values (403, admin auth required). **Expectation to confirm:** `loop_lag_ms` and room `tick_ms` should be single-digit ms while `ping_avg_ms` is 100+ — that gap is the network, confirming the server adds ~nothing.

## Fixes
1. **Platform / architecture (dominant):** origin is single-region us-west-2. To get central/east US players under ~100ms you need an origin closer to them (multi-region game servers / regional matchmaking). This platform pins the deployment to us-west-2, so a second region is an Emergent capability request — escalate to support.
2. **Code (E1):** given a single Oregon origin, reduce *perceived* lag with client-side prediction / entity interpolation / lag compensation if not already present, and surface the measured ping as "network latency" so it isn't read as a server fault. If/when multiple origins exist, add region-based server selection. Do NOT look to the server loop for wins here.
3. **User:** **A tier upgrade will NOT help** — CPU is ~4% of a 250m limit, memory is fine, nothing is throttled. Do not raise the tier to fix ping. Verify by (a) opening the admin Server Health panel (`/api/admin/server_health`) and comparing `loop_lag_ms`/`tick_ms` (expected single-digit) vs `ping_avg_ms` (100+), and (b) testing ping from a west-coast client — it should drop to ~20–40ms, proving the residual is distance to Oregon.

## Not the cause (ruled out)
CPU/CFS throttling, tier_0 limits, OOM, nginx WS buffering, event-loop saturation, replica count (2 up, both Ready), the 20Hz tick (off the ping path).
