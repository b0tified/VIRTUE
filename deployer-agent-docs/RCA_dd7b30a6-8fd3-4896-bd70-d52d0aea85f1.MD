# RCA — Blast Arena: in-game WS ping stuck at ~140 ms in production (was ~50 ms)

## Problem statement
Online-match ping (client sends WS `{"type":"ping"}`, backend replies `{"type":"pong"}`, client times the round-trip in Game.jsx) never drops below ~140 ms in prod, on every device/network. Used to be ~50 ms. Practice/offline (client-side) unaffected. Deployment: `blast-arena-servers`, active run `dd7b30a6-8fd3-4896-bd70-d52d0aea85f1`, template fastapi_react_mongo (ARM64), Cloudflare frontend, backend in AWS us-west-2 (cluster deployment-cluster-06).

## Root cause (confirmed mechanism)
The high ping is **event-loop scheduling latency**, not ping-handler work. The pong is produced by a trivial handler (server.py ~5948: `if mtype == "ping": await self._send(player, {"type":"pong", ...})`), so any delay is the single-threaded asyncio loop being too busy / CPU-throttled to service that `send` promptly.

That loop is heavily loaded and the pod is CPU-capped:

1. **Tier CPU ceiling is the dominant lever.** `get_tier`: tier_0 "Starter" → CPU request **50m**, **CPU limit 250m (¼ core)**, memory 200Mi/512Mi, **2 fixed replicas, HPA disabled**. A Python asyncio game server on ¼ of a core gets CFS-throttled whenever per-100ms CPU exceeds the quota — each throttle injects tens of ms of scheduling stall, which is exactly what inflates an otherwise-instant pong.

2. **One event loop drives a large, constant real-time workload.** At startup (server.py 1332–1363) the process launches 6 persistent 20 Hz game rooms (game/tdm/ranked/practice/practice_tdm/bigffa via `room.run()`) plus ~13 background loops (matchmaker, season, seeded-climb, synthetic-online, custom-titles, online-peak, ultimate-gooner, etc.), and spawns **dynamic per-user rooms** (offline/ranked-bot/party), each also a 20 Hz `room.run()`. Logs show ~30 disguised bots spawned per boot; bot AI is computed every tick. `TICK_RATE = 20`.

3. **Naive tick pacing.** `GameRoom.run()` (7609): `await self.tick(); await asyncio.sleep(1/20)` — a fixed 50 ms sleep *after* compute, with no drift compensation. Under CPU pressure effective tick period grows and every room's tick + every WS send compete on the same loop.

4. **Match-end DB writes sit on the hot path.** `end_match()` (called inline from `run()`, 7455–7525) `await`s, per real player, `db.users.find_one`, then `db.match_history.insert_many`, then a per-user retention prune (`find().sort().skip().limit()` + `delete_many`), then skin grants — all awaited inside the tick-driving loop. (Kill events correctly use the `_bg()` fire-and-forget helper at line 82; match-end does not.) Each Atlas round-trip is wall-clock time during which that room doesn't advance and the loop is juggling everyone else.

### Corroborating evidence
- Live `GET /api/` (a trivial counter JSON) measured **588 / 339 / 463 ms** across probes with ~26–35 players online; preview answers the same class of endpoint in ~1 ms. Production endpoint latency being hundreds of ms for near-zero work is consistent with loop saturation / CPU throttling, not network alone.
- `get_pod_events`: **no OOMKills, no CrashLoopBackOff**, running pod `restart_count=0`. The 503 startup-probe failure and nginx `connect() refused → 127.0.0.1:8001/health` entries are **boot-time only** (backend not yet listening). The constant `GET /health 404` is just probe noise (no `/health` route; app is under `/api`). So this is not a crash/OOM/restart issue.
- No explicit "slow tick"/"loop lag" warnings exist — the app does not instrument loop lag, so absence of such logs is not evidence of a healthy loop.

### Ruled out / secondary
- **Room leak:** NOT the cause. Per-user offline/ranked-bot/party rooms are torn down in the `ws_game` `finally` block (13335+ → `cleanup_offline_room_if_empty` / `cleanup_ranked_bot_room_if_empty` / party cleanup), which cancel the task and pop the dict. No `rooms` collection in Mongo (confirmed via list_collections) — rooms are purely in-memory and cleaned on disconnect.
- **Replicas / sticky WS:** 2 fixed replicas, each independently runs the *full* set of persistent rooms + background loops + bots, so adding replicas does **not** reduce per-pod baseline load. A WS connection is pinned to one pod for its lifetime (inherent to the TCP conn), so stickiness is not the latency cause; but in-memory per-pod rooms do mean casual/ranked matchmaking state is split across the 2 pods (a correctness caveat, not the ping cause).
- **Region routing:** Cloudflare edge → us-west-2 origin adds a fixed baseline RTT, but recent runs are redeploys to the same cluster/region, so routing does not explain a 50→140 ms *regression* that appeared over several deploys. The regression is consistent with the per-loop workload growing over time against a fixed 250m CPU cap.

> Note on confidence: the CPU-throttling mechanism is inferred from the tier's 250m limit + the heavy single-loop workload + production-only latency on a trivial endpoint. I could not read live CFS-throttle counters or per-pod CPU with the available tools, so that specific metric is inferred, not directly measured. The code paths above were read in a sandbox of this exact run's source but not runtime-benchmarked.

## Recommended fixes
### 1. Raise the tier (User — Deployment Panel → Resources)
tier_0 caps CPU at 250m (¼ core). Move to tier_1+ to give the event loop real CPU headroom; this is the most direct lever to remove the throttling that inflates pong latency. Re-measure in-game ping after the bump.

### 2. Get work off / spread the hot path (Code — E1)
- Move `end_match()` DB work (per-player `find_one`, `match_history.insert_many`, retention prune, skin grants) off the room's `run()` loop — wrap them with the existing `_bg()` / `asyncio.create_task` so a finishing match never stalls that room's ticks.
- Use drift-compensated tick scheduling in `run()` (compute next deadline as `start + n*interval` and sleep the remainder) instead of a flat `sleep(1/20)` after compute, so a slow tick doesn't cascade.
- Reduce per-tick CPU: throttle or idle-slow the 6 persistent + practice rooms when they have no real players (idle rooms needn't run full 20 Hz), and cap/cheapen per-bot AI cost per tick. Fewer busy 20 Hz loops = lower baseline loop occupancy = lower pong latency even before any tier change.

### 3. (Optional, architectural) Shared room state across replicas (Code — E1)
With 2 replicas and in-memory per-pod rooms, matchmaking/presence is split across pods. Not the ping cause, but worth addressing if cross-pod match consistency matters.
